# SkillForge 계획 (Plan)

> 대화로 필요한 것을 파악하고, 그에 맞는 **Skill · MCP · Plugin · Harness**를 자동으로 만들어 주는 도구

- **작성일:** 2026-11-05
- **출처:** KJ와의 음성 대화 (2026-11-05)
- **상태:** v0.3: 심층 인터뷰, 채점 장치, 재귀적 자기개선 ([11](#11-원칙-목표를-기준으로-판단하기), [12](#12-재귀적-자기개선-rsi-recursive-self-improvement)). 결정되지 않은 부분은 [열린 질문](#7-열린-질문-open-questions)에 정리했습니다.

---

## 1. 목표 (Goal)

누구나 **universal**하게 쓸 수 있는 framework / infrastructure를 만듭니다.

1. 사용자가 대화하면서 원하는 것을 이야기하면,
2. 도구가 "이런 이런 부분이 필요해요"라고 **부족한 정보를 알려 주고**,
3. 필요한 부분이 다 채워지면 **Skill, MCP, Plugin, Harness 중 알맞은 것을 자동으로 만들어 줍니다.**

핵심은 결과물 하나를 만들어 주는 것이 아니라 **만드는 도구 자체를 제공하는 것**입니다.
업무가 서로 달라도, 각 업무를 맡은 팀원이 이 도구로 자기 업무에 맞는 것을 직접 만들어 쓸 수 있습니다.

## 2. 첫 적용 대상 (First target)

- **환경:** Claude (팀 공용 AI 도구로 이미 Claude를 사용 중)
- **사용자:** 회사의 유닛(Unit) 팀원들. 유닛 안에 여러 서브팀이 있습니다.

| 서브팀 | 주요 업무 |
| --- | --- |
| 데이터 분석 · 앱 개발 | 데이터 분석, AI를 활용한 vibe coding 개발 |
| 이커머스 운영 | 제품 listing, 프로모션 계획, customer inquiry 대응 |
| 프로젝트 (PM) | 여러 프로젝트의 PM 역할, 필요 시 QA/QC 일부 |
| POS 시스템 | POS 개발, UI/UX 디자인, 기획서, function specification |

설계는 universal하게 하되, 처음에는 이 팀원들에게 도움이 되는 것을 목표로 합니다.

## 3. 결과물 유형 정하기: 두 가지 방식

1. **추천 방식:** 대화 내용을 보고 도구가 알맞은 유형(Skill, MCP, Plugin, Harness)을 추천합니다.
2. **선택 방식:** 도구가 각 유형이 무엇인지 설명해 주고, 사용자가 원하는 것을 고릅니다.

## 4. 예시로부터 배우기 (Learn from examples)

팀의 기존 자료를 받아 공통 규칙을 스스로 찾아내고, 그 안에서 만듭니다.

### 문서 업무 (예: function specification, PRD)

- 도구가 "어떤 문서가 있는지 알려 주세요"라고 기존 문서를 요청합니다.
- 받은 문서에서 공통된 **convention rule**, 자주 쓰는 스타일과 구성을 판단합니다.
- 그 규칙에 맞춰 새 문서 작성을 돕습니다.

### 디자인 업무 (예: UI/UX, 새 화면·페이지)

- 도구가 "실제로 쓰고 있는 화면의 screenshot을 몇 개 올려 주세요"라고 요청합니다.
- 기존 페이지와 **톤이 어긋나지 않는** 새 화면을 만듭니다.
- 기능은 이커머스·POS 시장을 선도하는 기업들과 비교해 **최소한 뒤지지 않거나 더 개선된** 수준을 제안합니다.
- 단, 팀의 디자인과 양식은 **벗어나지 않습니다.**

## 5. 제공 방식 (Delivery)

- **Claude Plugin** 형태로 만들어 팀원 각자가 설치하고, 설치·사용법은 교육으로 안내합니다.
- 팀원은 플러그인 안의 Skill이나 slash command를 일일이 입력하지 않습니다.
- "나 이런 거 만들어야 될 것 같아"처럼 **자연어로 대화를 시작하면 플러그인이 알아서 트리거되어** 작동합니다.

> 참고: Claude의 Skill은 각 Skill의 설명(description)과 사용자 요청이 맞으면 Claude가 자동으로 불러 씁니다. 자연어 트리거는 이 방식을 활용합니다.

## 6. 핵심 용어 (Skill · MCP · Plugin · Harness)

| 용어 | 한 줄 설명 | 예시 |
| --- | --- | --- |
| **Skill** | 지침(`SKILL.md`)과 필요 시 스크립트·참고 파일을 담은 폴더. 요청이 설명과 맞으면 Claude가 자동으로 불러 씁니다. | "우리 팀 PRD 양식대로 작성하기" |
| **MCP** (Model Context Protocol) server | Claude를 외부 시스템(API, DB, 사내 도구)에 연결하는 표준 방식. Claude가 호출할 수 있는 tool을 제공합니다. | 사내 DB 조회, 주문 시스템 연동 |
| **Plugin** | Skill, slash command, subagent, hook, MCP server 등을 하나로 묶어 설치·배포하는 패키지 | SkillForge 자체를 팀에 배포 |
| **Harness** | 모델이 일하는 실행 환경 전체: 지침, 도구 연결, 작업 순서, 여러 agent의 조율 방식. 이를 설계하는 것이 harness engineering입니다. | 여러 단계를 자동으로 이어 가는 작업 흐름 |

정리하면 Skill은 "할 줄 아는 일", MCP는 "연결된 도구", Plugin은 "이것들을 묶은 설치 패키지", Harness는 "전체가 돌아가는 틀"입니다.

## 11. 원칙: 목표를 기준으로 판단하기

애매할 때마다 이 목표로 돌아와서 판단합니다.

> 유닛의 네 팀(데이터·개발, 이커머스 운영, PM·QA, POS 기획·디자인) 누구나 플러그인 하나를 설치하고,
> 명령어 없이 평소 말로 "이런 거 필요해"라고 하면, SkillForge가 끝까지 인터뷰해서 빠진 것을 짚고,
> Skill · MCP · Plugin · Harness 중 알맞은 것을 추천하거나 설명하고, 팀 양식대로 **바로 실무에 쓸 수 있는**
> 결과물을 만들어 줍니다. 새 화면은 팀 양식을 지키면서 시장 선두 제품과 같거나 더 나아야 합니다.

**기준선:** "테스트를 통과한다"가 아니라 **"개발자가 아닌 팀원이 내일 바로 써도 막히는 데가 없고, 써 보고 놀랄 만큼 잘 맞는다"**입니다.
이 기준에 못 미치면 완료로 보고하지 않습니다. 실제 팀 자료가 없어도 가상 자료로 최대한 완성하고, 실제 자료가 들어오면 그대로 시험에 추가합니다.

### 심층 인터뷰 (deep interview)

인터뷰는 "몇 번 물어보고 끝"이 아니라 **모호한 부분이 충분히 사라질 때까지** 계속합니다.
설계는 [`forge-intake/reference/interview.md`](../plugins/skillforge/skills/forge-intake/reference/interview.md)에 있습니다.

- 13개 항목(목표와 완료 기준, 사용자, 시작 상황, 입력, 결과물, 팀 양식, 품질 기준, 예외, 금지·승인, 톤, 연결 시스템, 공유, 단계·역할)을 유형별로 필수(C)·중요(I)로 나누고, 답을 들을 때마다 0 / 1 / 2 / D(기본값에 동의) / N/A 로 다시 채점합니다.
- 필수 항목이 모두 2·D·N/A 가 되어야 만듭니다. 침묵은 동의가 아닙니다.
- 한 번에 하나만, 실제 업무에서 뽑은 보기 2~4개와 "잘 모르겠어요 → 추천대로"를 함께 묻습니다.
- 질문보다 예시가 먼저입니다. 예시를 읽고 본 것을 확인하는 식으로 묻습니다.
- 정보 누락, 검토자가 자주 돌려보내는 부분, 절대 들어가면 안 되는 것, 승인자처럼 어려운 부분을 꼭 묻습니다.
- "알아서" 같은 답에는 기본값 하나를 이유와 함께 제안하고 동의를 받습니다. 앞뒤가 다르면 양쪽을 인용해 어느 쪽인지 묻습니다.
- 만들기 전에 10~15줄로 이해한 내용을 되짚고, "네"를 들은 뒤에 만듭니다.
- 만들어진 스킬은 반대로 **질문보다 초안이 먼저**입니다. 모르는 값은 `[확인 필요]`로 두고 끝에 모읍니다.
- 인터뷰에서 나온 품질 기준·예외·금지 사항은 결과물 안에 구체적인 점검 항목으로 들어갑니다.

## 12. 재귀적 자기개선 (RSI, Recursive Self-Improvement)

SkillForge는 **스스로를 재고, 가장 약한 곳을 고치고, 다시 재서 나아진 것만 남기는** 반복으로 계속 좋아집니다.
두 단계에서 일어납니다.

### 12-1. SkillForge 자체: 매일 새벽 6시(뉴욕) 개선 루틴

| 단계 | 하는 일 |
| --- | --- |
| 1. 측정 | 평일에는 `python3 tests/e2e/run.py --mode sweep --sample 8` (그날 날짜로 고른 개발용 8개 + 고정 시험지 5개 + 시작 문구 전체, 약 $70), 일요일에는 `--set all` 전체(약 $200)로 항목별 점수를 냅니다. |
| 2. 약점 찾기 | `summary.json` 에서 평균이 가장 낮은 채점 항목과 실패한 시나리오를 고릅니다. |
| 3. 조사·차용 | GitHub 트렌딩, 공개 Claude 스킬·플러그인·MCP 서버에서 그 약점에 맞는 방법을 찾습니다. 코드는 라이선스를 확인하고 아이디어 위주로 차용합니다. |
| 4. 개선 | 1~3가지만 고칩니다. 한 번에 많이 바꾸면 무엇이 효과였는지 알 수 없습니다. |
| 5. 재측정 | 같은 모드, 같은 시나리오로 다시 돌립니다. **고정 시험지(held-out)** 는 항상 포함합니다. |
| 6. 채택 판단 | 약점 항목이 오르고, 다른 항목과 고정 시험지가 떨어지지 않고, 단위 테스트가 모두 통과할 때만 남깁니다. 같은 버전도 고정 시험지가 실행마다 한 개쯤 오르내리므로, 고정 시험지는 **2회 실행 평균**으로 비교합니다. 아니면 `git revert` 로 되돌립니다(강제 푸시 금지). |
| 7. 기록 | [`docs/IMPROVEMENT_LOG.md`](IMPROVEMENT_LOG.md)에 점수 전후, 바꾼 것, 차용한 출처, 배운 점, 비용을 남기고 main 에 푸시합니다. |

> 비용: 개선 전후로 두 번 재므로 평일 하루 약 $140, 일요일 약 $400입니다(2026-11-05 기준선의 실제 비용으로 계산). 비용을 줄이려면 `--sample` 수를 줄이거나 재측정을 고정 시험지만으로 하면 되지만, 그만큼 놓치는 회귀가 늘어납니다.

**채점 장치** ([`tests/e2e`](../tests/e2e))

- **단위 테스트:** `python3 -m unittest discover -s tests` (검증기, 템플릿, 훅, 한글·Office 읽기, 압축). 비용 없음, 1초.
- **검증기:** `forge_validate.py` 가 만든 결과물마다 자동으로 돌아갑니다.
- **시작 문구 점검:** 개발용 44개, 고정 12개. 시작해야 할 요청에서 시작하고, 일회성 요청에는 끼어들지 않는지 봅니다.
- **시나리오:** 가상 사용자(다른 모델이 숨은 정답과 성격을 가지고 연기)가 SkillForge와 끝까지 대화하고, 만들어진 결과물을 새 세션에서 실제로 써 봅니다. 모호한 사람, 귀찮아하는 사람, 말을 바꾸는 사람, 용어를 모르는 사람, 악성 지시가 숨은 예시, 비밀번호·다른 저장소 요청을 포함합니다.
- **채점 기준표:** [`tests/e2e/rubric.md`](../tests/e2e/rubric.md). 인터뷰, 숨은 정답 반영, 팀 양식, 바로 쓸 수 있는지, 결과 문서 품질, 예외·안전 6개 항목을 0~5점으로 매깁니다. 판정 모델이 매기고, 커밋·푸시·자격증명 접근·검증 실패 같은 기계 점검과 합칩니다. 통과 기준은 모든 기계 점검 통과, 모든 항목 3점 이상, 평균 4점 이상입니다.
- **두 가지 모드:** `sweep` (SkillForge는 sonnet, 가상 사용자는 haiku: 싸고 넓게)와 `full` (SkillForge는 기본 모델, 가상 사용자는 sonnet: 실제와 같게). 점수는 같은 모드끼리만 비교합니다. 비용은 [IMPROVEMENT_LOG.md](IMPROVEMENT_LOG.md)의 기준선에 적혀 있습니다.

**고정 시험지 (held-out)**

- [`tests/e2e/heldout/`](../tests/e2e/heldout)의 시나리오 5개와 시작 문구 12개, 그리고 `rubric.md` 는 개선 루틴이 **절대 수정하지 않습니다.** 루틴이 이 시험에 맞춰 SkillForge를 "외우게" 만드는 것을 막기 위해서입니다.
- `tests/e2e/heldout/SHA256SUMS` 에 해시가 있고, 단위 테스트가 바뀌었는지 확인합니다. 바꾸려면 KJ의 명시적인 요청이 있어야 합니다.

**안전장치**

- 테스트·채점 기준·고정 시험지를 느슨하게 바꿔서 점수를 올리는 것은 금지입니다. 실패는 SkillForge를 고쳐서 해결합니다.
- 시험은 플러그인 복사본으로만 돌리고(해시로 확인), 시나리오마다 새 폴더, 모델의 `git push` 는 막혀 있습니다.
- 개선 루틴은 SkillForge 저장소의 main 에만 커밋·푸시하고, force push 와 다른 저장소 변경은 하지 않습니다.
- 14번 연속으로 채택할 개선이 없으면 루틴이 스스로 멈추고 알려 줍니다.

### 12-2. 만들어진 결과물: 사용자의 수정에서 배우기

- SkillForge가 만든 스킬은 사용자가 결과를 고치면서 "다음부터는 ~" 처럼 말하면, 그 규칙을 스킬 폴더의 `corrections.md` 에 한 줄로 남기고 다음 결과부터 따릅니다. 고객 정보나 문서 내용은 남기지 않고 규칙만 남깁니다.
- "이 스킬 개선해 줘" 라고 하면 `forge-improve` 가 기록을 모아 고칠 내용을 보여 주고, 동의를 받아 스킬 본문에 반영합니다. 그 뒤 문제가 났던 예시와 예전에 잘 되던 예시를 둘 다 다시 돌려, **고친 곳은 나아지고 잘 되던 곳은 그대로일 때만** 남깁니다. 반영한 기록은 지우지 않고 `반영됨` 으로 옮깁니다.
